# 개발자별 알림 메시지 초안 만들기 (발송 전 단계)

`common-asset-notify`가 만든 영향도 정리 문서를 읽어, **개발자마다 받을 사내 채팅 메시지 초안**을 만들어 파일로 남긴다.

- 이 스킬은 **발송 전 단계**까지만 한다. 사내 채팅 연동 방식(API, 사용자 ID 체계)이 정해지지 않았기 때문이다.
  나중에 발송 단계를 붙일 때 이 스킬이 남긴 JSON을 읽어 보내기만 하면 되도록 만든다.
- 메시지 내용은 notify 문서의 `변경 내용`, `할 일`을 **그대로** 쓴다. 변경 내용을 다시 판정하거나 새로 해석하지 않는다.
- 발송, 채팅 사용자 ID 매핑, 발송 여부 추적은 하지 않는다.
- 전체 공지용 메시지의 **받는 곳**(전체 개발자 / 공지방)도 정하지 않는다. `unresolved`로 남기고, 채팅 연동 방식이 정해지면 발송 단계에서 정한다.

| 정리 문서의 자산 등급 | 메시지에서 |
|---|---|
| 🔴 / 🟡 / 🟢 (조사한 자산) | 해당 개발자에게 알린다. |
| ⚪ 신규 | 쓰는 개발자가 없으므로 개발자별 메시지는 없다. 대신 **전체 공지용 메시지**를 자산마다 하나 만든다. 받는 곳(전체 개발자 / 공지방)은 정하지 않는다. |

## 경로

- 입력: `common-repo/asset-index/notifications/<YYYYMMDD>-<해시7들>.md` (notify가 만든다. 같은 폴더의 `.json` 파일은 옛 형식이므로 쓰지 않는다.)
- 프로젝트 목록: `common-repo/asset-index/projects.json` (`path`, `owner`를 쓴다. 읽기만 한다.)
- 정리집: `common-repo/asset-index/asset-index.json` (신규 자산의 설명 `purpose`를 읽는 데만 쓴다. 읽기만 한다.)
- 출력: `common-repo/asset-index/messages/<정리 문서 이름(확장자 제외)>.json`
- 미처리 판단: 정리 문서 `X.md`에 대응하는 `messages/X.json`이 **없으면** 미처리다. (별도 상태 필드는 두지 않는다.)

## 핵심 원칙

1. **프로젝트 저장소는 읽기만 한다.** 수정, 커밋, 브랜치 변경을 하지 않는다. `git -C <프로젝트> blame`, `log`만 쓴다.
2. **정리 문서에 있는 것만 쓴다.** 문서에 없는 사용처, 개발자, 할 일을 만들지 않는다.
3. **수신자는 코드로 확인한다.** 이름은 정리 문서에서, 이메일은 blame에서 얻는다. 확인되지 않으면 지어내지 않고 `null`로 두고 미리보기에 표시한다.
4. **채팅 ID는 정하지 않는다.** 채팅 사용자 ID 칸은 `unresolved`로 남긴다. 이메일에서 추측해 만들지 않는다.
5. **공개되는 메시지에는 깨끗한 문장만 남긴다.** `(AI 추론)` 같은 표시, 이메일, 커밋 메시지는 메시지 본문에 넣지 않는다.
6. **사용자 확인은 두 번 받는다: 파일 생성(4단계), push(6단계).**
7. **셸 명령은 한 번에 하나만 실행한다.** `;`, `&&`, `&`로 잇지 않는다. `cd` 없이 `git -C <경로>`로 실행한다.

## 순서

### 1. 처리할 정리 문서 모으기
- `asset-index/notifications/*.md` 목록과 `asset-index/messages/*.json` 목록을 비교해, 대응하는 메시지 파일이 없는 `.md`만 고른다.
- **범위 지정:** 요청에 문서 이름이나 커밋 해시가 있으면 그 문서만 처리한다. 나머지는 열지 않는다.
  (`common-asset-notify` 8단계에서 이어 호출된 경우 방금 만든 정리 문서가 범위다. 따로 "알림 메시지 만들어줘"라고 요청받으면 범위가 없으므로 미처리 문서를 모두 처리한다.)
- 고른 문서를 읽는다. 신규(⚪)만 있는 문서도 처리한다. (개발자별 메시지 없이 전체 공지용 메시지만 만든다.)
- 처리할 문서가 없으면 "새로 만들 메시지가 없습니다"라고 알리고 끝낸다.
- 조사한 자산(🔴/🟡/🟢)이 있는 문서가 있으면 `projects.json`을 읽는다. 없으면 "projects.json이 필요합니다"라고 안내하고 끝낸다. (신규만 있는 문서만 처리할 때는 읽지 않는다.)

### 2. 정리 문서 해석
문서에서 아래를 읽는다.
- 자산 섹션마다: 자산 이름, 등급 이모지, 커밋 해시, `변경 내용`, `할 일`, 영향 대상 표(프로젝트, `파일:줄`, 사용 방식, 조치, 작성자)
- 신규(⚪) 자산 섹션: 자산 이름, 커밋 해시
- `관련 개발자` 표: 개발자 이름, 프로젝트, `(담당자)` 여부 (조사한 자산이 있을 때만 있다)
- 표 아래 인용 블록(`>`)의 안내 문장은 해당 자산의 **참고 문구**로 보관한다. (예: 복사본은 자동 반영되지 않는다는 설명)

### 3. 수신자 확인과 메시지 만들기

**3-1. 개발자(작성자) 이메일 확인**
영향 대상 표의 행마다, 해당 프로젝트의 `projects.json` 경로에서 실행한다.
```
git -C <프로젝트 경로> blame -L <줄>,<줄> --porcelain -- <파일>
```
- 출력의 `author`가 표의 작성자 이름과 같으면 `author-mail`(앞뒤 `<>` 제거)을 이메일로 쓴다.
- `파일:줄`에 줄이 없는 행(복사본 파일 자체)은 `git -C <프로젝트 경로> log -1 --format="%an|%ae" -- <파일>`로 확인한다.
- 이름이 다르거나 blame이 실패하면 이메일을 `null`로 두고 그 수신자에 `idNote: "코드 작성자와 문서의 이름이 달라 확인 필요"`를 적는다. 이메일을 추측하지 않는다.
- 같은 사람은 이메일 기준(이메일이 `null`이면 이름+프로젝트 기준)으로 한 명으로 묶는다.

**3-2. 프로젝트 담당자(PL)**
`관련 개발자` 표에서 `(담당자)`가 붙은 사람은 `projects.json`의 해당 프로젝트 `owner`(이름, 이메일)를 쓴다. 문서의 이름과 `owner.name`이 다르면 `owner`를 따르고 미리보기에 알린다.

**3-3. 수신자별 메시지**
수신자 한 명(개발자 또는 PL)당 **메시지 한 통**을 만든다. 여러 자산·여러 프로젝트에 해당하면 한 통에 모은다.

- **개발자 메시지**: 그 사람의 코드 위치만 담는다.
- **PL 메시지**: 자기 프로젝트의 영향 대상을 요약한다. (몇 곳, 누가 어디를 쓰는지)

메시지 본문은 채팅에 맞게 **평문**으로 쓴다. 마크다운 표·제목은 쓰지 않는다. 구성은 아래 순서를 따른다.

```
[공통 변경] <자산 이름> (<등급 한글: 수정 필요 / 확인 필요 / 기능 추가>)

<변경 내용 그대로>

사용 예상 위치
- <프로젝트> <파일:줄> (<사용 방식 한글>)
- ...

확인 사항
- <할 일 그대로>

<참고 문구가 있으면 한 줄>

상세: <정리 문서 파일 이름(.md 포함)>
```

- **어조는 담백하게 쓴다.** 안내문 같은 권유("~해 보세요", "~하면 좋겠습니다")나 감탄·인사말을 쓰지 않는다. 사실과 할 일만 짧게 적는다.
- 소제목은 `사용 예상 위치`, `확인 사항`으로 고정한다. 스캔은 코드 검색 결과이므로 "쓰는 곳"으로 단정하지 않고 "예상 위치"로 쓴다.
- `확인 사항`은 조치에 따라 문장 앞을 구분한다. 수정 필요 건은 `수정 필요:`, 확인 필요 건은 `확인 필요:`로 시작한다. 둘 다 있으면 수정 필요를 먼저 쓴다. `behavior` 항목은 `확인 필요:`로 시작하고, `compatible` 항목은 구분 없이 할 일만 적는다.
- 같은 줄에 같은 파일의 줄이 여럿이면 `EmployeeService.java:8, 12`처럼 한 줄로 합친다.
- 정리 문서 이름은 확장자 `.md`까지 빠짐없이 적는다.
- 자산이 여러 개면 `[공통 변경]` 머리말은 한 번만 쓰고, 자산별로 `── <자산 이름> (<등급>) ──` 구분선 아래에 위 내용을 반복한다.
- 등급 표시는 이모지 대신 한글(`수정 필요`, `확인 필요`, `기능 추가`)을 쓴다. 채팅 환경에서 이모지가 어떻게 보일지 모르기 때문이다.
- `breaking`에서 조치가 `🔴 수정 필요`인 위치와 `🟡 확인 필요`인 위치는 **나눠서** 적는다. 한 사람이 둘 다 해당하면 수정 필요를 먼저 쓴다.
- 코드·파일 경로는 그대로 적는다. 길이는 자산당 10줄 안팎으로 유지한다.

**3-4. 신규 자산의 전체 공지용 메시지**
신규(⚪) 자산마다 메시지 한 통을 만든다. 수신자는 없고 받는 곳은 `unresolved`다.
- 자산 설명: `asset-index.json`을 통째로 읽지 않고 `"name": "<자산 이름>"`을 검색해 그 항목의 `purpose`만 읽는다. 항목이나 `purpose`가 없으면 설명 줄을 뺀다. 지어내지 않는다.
- 본문은 아래처럼 쓴다. 담백한 어조 규칙은 3-3과 같다.
  ```
  [공통 신규] <자산 이름>

  새 공통 자산이 추가되었습니다.
  <purpose 그대로>

  상세: <정리 문서 파일 이름(.md 포함)>
  ```
- 개발자별 메시지와 달리 사용 위치, 확인 사항은 넣지 않는다. (쓰는 곳이 없다.)

### 4. 미리보기 (사용자 확인 후)
저장할 내용을 **채팅 본문에 마크다운 그대로** 보여 주고, 질문 도구로 **"이대로 메시지 초안 파일을 만들까요?"** 한 줄만 묻는다.
질문 도구가 없으면 같은 질문을 본문 마지막 줄에 적고 답을 기다린다.

- 전체를 코드 블록으로 감싸지 않는다. 단, **메시지 본문 하나하나는 코드 블록**으로 보여 준다. (평문 그대로 복사해 쓰는 글이기 때문이다.)
- 구성: 맨 위에 인용 블록 한 줄(`저장될 파일: asset-index/messages/<이름>.json`) → 수신자 요약 표(수신자, 프로젝트, 이메일 확인 여부, 포함 자산) → 수신자별 메시지(소제목 + 코드 블록) → (신규가 있으면) `전체 공지용 (받는 곳 미정)` 소제목 아래 자산별 메시지(코드 블록) → `---` 뒤에 확인이 필요한 항목(이메일 `null`, 이름 불일치, 담당자 이름 불일치)과 커밋 메시지.
- 질문 전 확인: 바로 위 응답 본문에 수신자별 메시지 전문이 있는가? 없으면 질문하지 말고 먼저 출력한다.
- 수정 요청이 있으면 고친 뒤 미리보기를 다시 보여 주고 다시 묻는다. 거절하면 아무 파일도 만들지 않는다.
- 이메일이 `null`인 수신자가 있어도 미리보기에서 알리고, 승인되면 `null`인 채로 저장한다. (채팅 ID 매핑 단계에서 처리한다.)

### 5. 파일 생성과 커밋
승인받은 내용 **그대로** 만든다.
- `asset-index/messages/<정리 문서 이름>.json`을 만든다. (UTF-8, 들여쓰기 2칸) 형식은 아래 [메시지 파일 형식]을 따른다.
- 올바른 JSON인지 확인한다. (common-repo에서 실행)
  `node -e "JSON.parse(require('fs').readFileSync(process.argv[1],'utf8')); console.log('JSON OK')" <메시지 파일>`
- 메시지 파일**만** 커밋한다.
  ```
  git -C common-repo add <메시지 파일>
  git -C common-repo commit -m "<제목>" -m "<본문>" -- <메시지 파일>
  ```
  - 제목: `docs: 개발자별 알림 메시지 초안 (<정리 문서 이름>)`
  - 본문: `- 수신자 <N>명 (개발자 <K>명, 담당자 <P>명), 이메일 미확인 <U>명` 과 `- 전체 공지용 <B>건`. 해당 없는 줄은 쓰지 않는다.
  - 커밋 직후 `git -C common-repo log -1 --format=%B`로 한글이 깨지지 않았는지 확인한다.

### 6. push 확인
- `git -C common-repo log --oneline @{u}..HEAD`로 push 안 된 커밋을 확인한다. upstream이 없으면 묻지 않고 보고에 적는다.
- 있으면 목록을 보여 주고 **"push할까요?"** 를 한 번만 묻는다.

### 7. 결과 보고
- 만든 메시지 파일 이름
- 수신자 수 (개발자, 담당자), 이메일을 확인하지 못한 수신자
- 전체 공지용 메시지 수 (받는 곳은 미정)
- "발송은 하지 않았습니다. 사내 채팅 연동 방식이 정해지면 이 파일을 읽어 보내는 단계를 추가합니다."
- push 결과

## 메시지 파일 형식

```json
{
  "id": "20261112-b6395ec",
  "createdAt": "2026-11-12T15:30:00+09:00",
  "sourceNotification": "20261112-b6395ec.md",
  "status": "draft",
  "broadcasts": [
    {
      "asset": "DateTimeUtils",
      "commit": "b6a0f67",
      "grade": "new",
      "target": "unresolved",
      "text": "[공통 신규] DateTimeUtils\n\n..."
    }
  ],
  "messages": [
    {
      "recipient": {
        "name": "김개발",
        "email": "kim.dev@example.com",
        "role": "author",
        "projects": ["shop-app"],
        "chatId": "unresolved",
        "idNote": null
      },
      "assets": [
        { "asset": "Pagination", "grade": "breaking", "commit": "b6395ec", "action": "required" }
      ],
      "locations": [
        { "project": "shop-app", "file": "frontend/src/pages/OrderList.tsx", "line": 13, "usageKind": "import", "action": "required" }
      ],
      "text": "[공통 변경] Pagination (수정 필요)\n\n..."
    }
  ]
}
```

- `broadcasts`: 신규 자산의 전체 공지용 메시지. `target`은 항상 `"unresolved"`(전체 개발자 / 공지방 미정). 신규가 없으면 빈 배열 `[]`. 조사한 자산이 없으면 `messages`도 빈 배열 `[]`.
- `status`는 항상 `draft`다. (발송 단계가 생기면 그 단계가 바꾼다.)
- `role`: `author`(코드 작성자) 또는 `owner`(프로젝트 담당자).
- `action`: `required`(수정 필요), `review`(확인 필요, `behavior` 포함), `none`(`compatible`처럼 구분 없음).
- `chatId`는 항상 `"unresolved"`다. `idNote`는 이메일을 확인하지 못했을 때만 문장을 넣고, 아니면 `null`.
- `text`는 승인받은 메시지 본문 그대로다. 줄바꿈은 `\n`.

## 하지 말 것
- 사내 채팅이나 메일, 메신저로 보내지 않는다. 발송 코드나 호출 예시도 만들지 않는다.
- 채팅 사용자 ID를 만들거나 추측하지 않는다.
- 프로젝트 저장소를 수정하거나, 프로젝트 저장소에서 커밋·checkout·pull 하지 않는다.
- 정리 문서(`notifications/*.md`), 변경 기록(`changes/*.json`), 정리집(`asset-index.json`)을 고치지 않는다.
- 신규 자산에 대해 개발자별 메시지를 만들지 않는다. (전체 공지용 메시지만 만든다.)
- 신규 자산 설명(`purpose`)을 지어내지 않는다. `asset-index.json`에 없으면 설명 줄을 뺀다.
- 정리 문서에 없는 사용처·개발자·할 일을 넣지 않는다. 메시지 본문에 이메일을 넣지 않는다.

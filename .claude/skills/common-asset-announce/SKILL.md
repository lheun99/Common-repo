# 공통 변경 정리 자료 작성

공통 자산의 변경을 **개발팀 전체가 한 번에 볼 수 있는 정리 자료**로 만든다.
공지나 공유 시간에 그대로 쓰거나, PPT로 옮겨 쓸 수 있다.
공통팀이 PPT와 공지를 직접 쓰던 일을 줄이는 것이 목적이다. 공통팀은 정리 자료를 **검토**만 한다.

- 결과물은 장(슬라이드) 단위로 나눈 Markdown 정리 자료다. (`asset-index/announcements/<id>.md`)
  PPT 파일은 만들지 않는다. 정리 자료의 한 장이 PPT 한 장에 해당하도록 쓴다.
- 결과물은 미리보기, 파일, 커밋 메시지, 결과 보고 어디서든 **"정리 자료"** 라고만 부른다. 다른 이름을 쓰지 않는다.
- 내용은 이미 만들어진 기록에서 가져온다. 소스를 다시 분석해 새 사실을 만들지 않는다.
  - 무엇이 바뀌었나: `asset-index/changes/*.json` (common-asset-sync가 만든다)
  - 자산 설명, 사용 예: `asset-index/asset-index.json`
  - 영향 프로젝트: `asset-index/notifications/*.json` (common-asset-notify가 만든다. 없으면 해당 부분을 뺀다)

## 핵심 원칙

1. **기록에 있는 내용만 쓴다.** 변경 기록, 정리집, 알림 파일에 없는 사실을 더하지 않는다.
   문장을 다듬거나 순서를 바꾸는 것은 된다.
2. **공개되는 정리 자료에는 깨끗한 문장만 남긴다.** `(AI 추론)`, 근거 메모 같은 표시를 넣지 않는다.
3. **사용자 확인은 두 번 받는다: 정리 자료 저장(4단계), push(6단계).**

## 순서

### 1. 범위 정하기
- 기본 범위: `asset-index/changes/*.json` 중 **`announcement` 필드가 없는** 기록 전부. (아직 정리 자료에 넣지 않은 변경)
- 사용자가 기간을 말하면("이번 주", "10월") `committedAt`으로 거른다. 그 경우에도 이미 정리 자료에 넣은 기록은 뺀다.
  사용자가 "다시", "전부"라고 하면 이미 넣은 기록도 포함한다.
- 각 기록의 `changes` 중 `grade`가 `docs`인 항목은 뺀다.
- 남은 항목이 없으면 "정리할 변경이 없습니다"라고 알리고 끝낸다.
- 범위(기간, 커밋 수, 항목 수)를 한 줄로 알린 뒤 다음 단계로 간다. 범위는 따로 묻지 않는다.

### 2. 자료 모으기
항목마다 아래를 모은다.
- 변경 기록: `grade`, `summary`, `details`(before/after), `action`, `commit`, `committedAt`, (`affectedApi`)
- 정리집의 같은 `name` 항목: `purpose`, `props`/`usage`/`api`, `detail`의 `[사용 예]`·`[동작]`·`[주의]`·`[API]`, `related`
- 알림 파일: 이 커밋·자산이 들어 있는 `notifications/*.json`의 `items[].targets`, `candidates`
  - 프로젝트별 곳 수만 쓴다. 파일·줄·개인 이름은 정리 자료에 넣지 않는다. (팀 전체가 보는 자료다. 개인별 안내는 알림이 한다.)
- 같은 자산이 범위 안에서 여러 번 바뀌었으면 하나로 묶고, 최종 상태 기준으로 쓴다. `details`는 시간 순서로 모두 보여 준다.

### 3. 정리 자료 구성
아래 [정리 자료 형식]대로 전체를 만든다. 아직 파일에 쓰지 않는다.

### 4. 미리보기 (사용자 확인 후)
정리 자료 전문을 **채팅 본문**에 먼저 출력한 뒤, 질문 도구로 **"이대로 정리 자료를 저장할까요?"** 한 줄만 묻는다.
질문 창에는 긴 내용이 보이지 않는다.
**질문 전 확인**: 바로 위 응답 본문에 정리 자료 전문(표지부터 마무리까지)이 있는가? 없으면 질문하지 말고 정리 자료부터 출력한다.
- 사용자가 수정을 요청하면 고친 뒤 정리 자료를 다시 보여 주고 다시 묻는다.
  사용자가 넣어 달라는 내용은 기록에 없더라도 공통팀이 확인한 내용으로 보고 반영한다.
- 거절하면 아무 파일도 만들지 않는다.

### 5. 저장과 커밋
- `asset-index/announcements/<id>.md`로 저장한다. (UTF-8)
  - `<id>`: `<YYYYMMDD>-<간단한 설명>(<기능 이름>)`. 날짜는 만든 날. 커밋 해시는 넣지 않는다.
    - `<간단한 설명>`: 이 정리 자료가 무엇에 관한 것인지 한글로 짧게 (5~15자). 단어 사이는 공백으로 띄운다.
      변경 내용이 하나면 그 변경을, 신규 위주면 기능을 설명한다.
    - `<기능 이름>`: 들어간 자산 이름. 여러 자산이 한 기능이면 그 기능을 대표하는 이름 하나, 서로 관계없는 자산이 섞이면 `<첫 자산> 외 <N>`.
    - 예:
      - Toast 자동 닫힘 시간 변경 → `20261022-토스트 자동 닫힘 시간 변경(Toast)`
      - FileController·FileStorageService·FileUploadResult·FileUpload 신규 → `20261015-파일 업로드 다운로드 추가(FileUpload)`
      - Toast, Pagination, Spinner 변경이 섞임 → `20261022-공통 자산 변경 모음(Toast 외 2)`
    - 영문·숫자·한글, 공백, 날짜 뒤의 `-`, 괄호만 쓴다. `/`, `.`은 쓰지 않는다.
    - 같은 이름의 파일이 이미 있으면 괄호 뒤에 `-2`, `-3`을 붙인다.
    - 파일 이름에 괄호·공백이 있으므로 git 명령에서는 경로를 따옴표로 감싼다.
    - 4단계 미리보기 맨 위에 `저장 파일: asset-index/announcements/<id>.md`를 보여 준다. 사용자가 이름을 바꿔 달라고 하면 그대로 따른다.
- 포함한 변경 기록 파일마다 `announcement` 필드에 `<id>`를 넣는다. 파일 편집 도구로 이 필드만 추가한다.
  다른 필드는 건드리지 않는다. JSON이 올바른지 확인한다. (common-repo에서 실행)
  `node -e "for (const f of process.argv.slice(1)) JSON.parse(require('fs').readFileSync(f,'utf8')); console.log('JSON OK')" <변경 기록 파일들>`
- 정리 자료와 고친 변경 기록 파일**만** 커밋한다. 경로는 하나씩 적는다.
  ```
  git -C common-repo add <정리 자료> <변경 기록 파일들>
  git -C common-repo commit -m "<제목>" -m "<본문>" -- <정리 자료> <변경 기록 파일들>
  ```
  - 제목: `docs: 공통 변경 정리 자료 작성 (<id>)`
  - 본문: `- 범위: <첫 커밋 시각 날짜> ~ <마지막 커밋 시각 날짜>, 커밋 <N>개 (<해시7들>)` 와 `- 항목: 비호환 a, 동작 변경 b, 호환 추가 c, 신규 d`
    (파일 이름에 해시가 없으므로 어떤 커밋을 담았는지는 본문의 해시로 남긴다.)
  - 메시지는 `-m`을 두 번 써서 명령 인자로 넘긴다. 커밋 직후 `git -C common-repo log -1 --format=%B`로 한글이 깨지지 않았는지 확인한다.

### 6. push 확인
- `git -C common-repo log --oneline @{u}..HEAD`로 push 안 된 커밋을 확인한다. upstream이 없으면 묻지 않고 보고에 적는다.
- 있으면 커밋 목록(`해시 제목` 한 줄씩)을 채팅 본문에 먼저 출력한 뒤 **"위 커밋을 push할까요?"** 를 한 번만 묻는다.

### 7. 결과 보고
- 정리 자료 파일 경로
- 범위와 항목 수 (등급별)
- 영향 프로젝트 정보가 없어서 뺀 항목 (알림을 아직 안 만든 변경)
- push 결과

## 정리 자료 형식

- 장은 `---` 한 줄로 나눈다. 장마다 `## 제목`으로 시작한다.
- 한 장의 본문은 **PPT 한 장에 들어갈 분량**으로 쓴다. 불릿은 5개 이하, 코드는 8줄 이하.
- 장마다 끝에 `> 설명 메모:`로 이 장에서 짚어 줄 내용을 1~3문장 쓴다. (공유 시간에 설명하거나 PPT 노트로 옮길 때 쓴다)
- 등급 표시는 `[비호환]`, `[동작 변경]`, `[호환 추가]`, `[신규]`를 쓴다.
- 순서: 표지 → 한눈에 보기 → 비호환 → 동작 변경 → 호환 추가 → 신규 → 마무리. 같은 등급 안에서는 커밋 시각 순.

### 장 종류

**표지** (1장)
```
# 공통 자산 변경 정리
<YYYY-MM-DD> · 공통팀
범위: <첫 날짜> ~ <마지막 날짜> (커밋 <N>개)
```

**한눈에 보기** (1장)
- 등급별 표: 자산 이름, 한 줄 요약, 개발팀이 할 일 수준(수정 필요 / 확인 필요 / 참고 / 도입 검토)
- 비호환이 있으면 맨 위에 "수정이 필요한 변경이 <N>건 있습니다" 한 줄

**비호환·동작 변경 항목** (자산당 1~2장)
1. `## [비호환] <자산명> — <한 줄 요약>`
   - 무엇이 바뀌었나 (`details`를 불릿으로)
   - 변경 전/후 코드: `details`의 before/after를 코드 블록 두 개로
   - 영향 받는 API·메서드: `affectedApi` (여러 파일로 된 기능일 때만)
   - 할 일: `action`
   - 영향 프로젝트: `shop-app 2곳, admin-app 1곳(복사본)` (알림 파일이 있을 때만)
2. 복사본 사용처가 있으면 "복사해서 쓰는 곳은 자동으로 반영되지 않습니다"를 넣는다.

**호환 추가 항목** (여러 자산을 한 장에 묶어도 된다)
- 자산마다: 추가된 것, 사용 예 한 줄

**신규 항목** (자산당 1장)
1. `## [신규] <자산명> — <purpose>`
   - 이런 때 쓰세요: `[동작]`·`[주의]`·`purpose`에서 2~3개
   - 사용 예: 정리집 `[사용 예]` 그대로
   - API: 정리집 `api` (있을 때만)
   - 함께 쓰는 자산: `related` (있을 때만)
   - 대체할 수 있는 곳: 알림 파일의 `candidates`를 프로젝트별 곳 수로 (있을 때만)

**마무리** (1장)
- 자세한 내용은 공통 자산 탐색 페이지에서 확인할 수 있다는 안내
- 개별 수정 요청은 담당자에게 따로 알림이 갔다는 안내 (알림 파일이 있을 때만)
- 문의: 공통팀

### 정리 자료 예

````markdown
# 공통 자산 변경 정리
2026-10-14 · 공통팀
범위: 2026-10-14 ~ 2026-10-14 (커밋 1개)

> 설명 메모: 이번 주 공통 자산 변경 사항을 정리했습니다.

---

## 한눈에 보기

수정이 필요한 변경이 1건 있습니다.

| 구분 | 자산 | 내용 | 할 일 |
|---|---|---|---|
| [비호환] | Pagination | onChange 인자가 객체로 바뀜 | 수정 필요 |

> 설명 메모: 비호환 변경 1건이 있어 해당 화면은 수정이 필요합니다.

---

## [비호환] Pagination — onChange 인자가 객체로 바뀜

- onChange 인자가 page 숫자에서 { page, pageSize } 객체로 바뀌었습니다.
- pageSize prop이 추가되었습니다. (선택, 기본 20)
- 전체 페이지가 1 이하이면 표시되지 않습니다.

변경 전
```tsx
onChange: (page: number) => void
```
변경 후
```tsx
onChange: (value: { page: number; pageSize: number }) => void
```

**할 일**: onChange 핸들러가 객체를 받도록 수정하세요. 예: `onChange={({ page }) => setPage(page)}`
**영향 프로젝트**: shop-app 2곳, admin-app 1곳(복사본 — 자동 반영되지 않음)

> 설명 메모: 해당 화면 담당자에게는 위치와 함께 개별 알림이 갔습니다.
````

## 하지 말 것
- PPT·PDF 등 다른 형식의 파일을 만들지 않는다.
- 기록에 없는 사실을 정리 자료에 넣지 않는다. (사용자가 요청한 내용은 예외)
- 정리 자료에 개인 이름, 파일 경로, 줄 번호를 넣지 않는다.
- 변경 기록의 `announcement` 외 필드, 정리집, 알림 파일을 고치지 않는다.

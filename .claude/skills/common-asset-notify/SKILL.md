# 공통 변경 영향도 조사 및 개발자 정리

사용처 스캔과 담당자 파악(2~3단계)은 `tools/impact_scan.py`가 한 번에 처리한다.
AI는 스크립트 결과 JSON을 읽고 판단·문서 작성만 한다. 스크립트가 쓰는 탐지·담당자 규칙은 아래 [스크립트 결과 읽는 법]에 요약돼 있다.

공통 자산의 변경이 **어느 프로젝트의 어느 코드에 영향을 주는지** 실제 소스를 스캔해 찾고,
그 코드를 작성한 개발자와 프로젝트 담당자를 **정리**해 md 문서로 남긴다.

| 변경 기록의 등급 | 하는 일 |
|---|---|
| `new` (신규) | 조사하지 않는다. 문서에 "신규"로 한 줄만 올린다. |
| `breaking` / `behavior` / `compatible` (변경, 수정) | 사용처를 스캔해 영향 대상을 찾고, 관련 개발자를 정리한다. |
| `docs` | 대상에서 뺀다. |

- 개발자가 AI로 만들었든 직접 짰든 상관없이 **코드 기준**으로 찾는다.
- 결과는 md 문서(`asset-index/notifications/`)로 남긴다. 알림 발송(PMS, 메일, 메신저)은 하지 않는다.
  (개발자별 채팅 메시지 초안은 `common-asset-dispatch`가 이 문서를 이어받아 만든다. 마지막 8단계에서 이어 갈지 묻는다.)
  (폴더 이름과 변경 기록의 `notified` 필드 이름은 이전 이름 그대로 쓴다. 뜻은 "영향도 조사·개발자 정리를 마침"이다.)
- 신규 자산의 대체 후보(기존에 직접 구현한 곳) 탐색은 하지 않는다.
- 변경 내용 자체(무엇이 어떻게 바뀌었나)는 `common-asset-sync`가 남긴 변경 기록을 그대로 쓴다. 다시 판정하지 않는다.

## 경로

- 변경 기록: `common-repo/asset-index/changes/<해시7>.json` (common-asset-sync가 만든다)
- 정리집: `common-repo/asset-index/asset-index.json` (자산의 path·종류 확인용, 읽기만 한다)
- 프로젝트 목록: `common-repo/asset-index/projects.json` (공통팀이 관리한다)
  - `path`는 common-repo 기준 상대 경로이거나 절대 경로다.
- 정리 문서: `common-repo/asset-index/notifications/<YYYYMMDD>-<해시7들>.md`

## 두 가지 모드

| 모드 | 요청 예 | 하는 일 | 파일 생성 |
|---|---|---|---|
| **정리** | "영향도 조사해줘", "관련 개발자 정리해줘", sync 이후 이어서 진행 | 미처리 변경 기록 → 스캔 → 개발자 정리 → 정리 문서 | O (승인 후) |
| **조회** | "Pagination 쓰는 곳 찾아줘", "Holiday 영향도 알려줘" | 지정한 자산만 스캔 → 결과를 채팅으로 보고 | X |

조회 모드는 아래 2~3단계(스크립트 실행, 결과 확인)만 하고 결과를 표로 보여 준 뒤 끝낸다. 커밋하지 않는다.
이미 정리를 마친(`notified: true`) 자산도 조회할 수 있다. 변경 기록은 고치지 않는다.

## 핵심 원칙

1. **프로젝트 저장소는 읽기만 한다.** 수정, 커밋, 브랜치 변경을 하지 않는다.
2. **커밋된 코드만 스캔한다.** `git -C <프로젝트> grep`, `ls-files`, `blame`을 쓴다. (작업 트리의 미커밋 변경은 보지 않는다.)
3. **찾은 것만 적는다.** 스캔에서 나오지 않은 사용처나 담당자를 지어내지 않는다.
4. **공개되는 결과물에는 깨끗한 문장만 남긴다.** 정리 문서에 `(AI 추론)` 같은 표시를 넣지 않는다.
5. **사용자 확인은 두 번 받는다: 정리 문서 생성(4단계), push(6단계).** (8단계의 이어가기 질문은 다음 스킬로 넘어갈지 묻는 것이며 이 두 번에 포함하지 않는다.)
6. **셸 명령은 한 번에 하나만 실행한다.** `;`, `&&`, `&`로 잇지 않는다. 스캔은 아래 스크립트 한 번이면 끝난다.
7. **스크립트 결과를 고치지 않는다.** 스크립트가 찾지 못한 사용처·담당자를 AI가 지어서 넣지 않는다. 판단이 필요한 곳만 3단계의 확인 규칙을 따른다.

## 순서 (정리 모드)

### 1. 처리할 변경 기록 모으기
- `asset-index/changes/*.json`에서 내용 검색으로 `"notified": false`가 들어 있는 파일만 골라 **그 파일만** 읽는다. `notified`가 `true`인 파일은 열지 않는다. 커밋 시각(`committedAt`) 순으로 정렬한다.
- **범위 지정:** 요청에 자산 이름이나 커밋 해시가 있으면(예: "Holiday만 영향도 조사해줘", "49f35f8만 진행해줘") 그 자산·커밋의 변경 기록만 처리한다.
  나머지 `notified: false` 파일은 열지도 고치지도 않고, 그대로 미처리로 남긴다. 범위가 없으면 전부 처리한다.
  (자산 이름은 변경 기록 파일을 열기 전에 `"asset": "<Name>"` 내용 검색으로 해당 파일만 고른다.)
- **같은 자산은 하나로 묶는다:** 처리할 기록 중 같은 자산(`asset`)이 여러 건이면 한 항목으로 합쳐 **최신 상태 기준으로 한 번만** 스캔한다.
  - 등급은 가장 높은 것을 쓴다. (`breaking` > `behavior` > `compatible` > `new`)
  - 요약·할 일은 기록들의 내용을 커밋 시각 순으로 모아 보여 준다. 문서에는 묶인 커밋 해시를 모두 적는다.
  - 스캔 단서(`scanHints`, `affectedApi`)는 묶인 기록의 것을 합친다.
  - 묶인 기록이 모두 `new`일 때만 신규 항목이다. `new`와 다른 등급이 섞여 있으면 그 다른 등급 항목으로 조사한다.
  - 5단계에서 묶인 기록 파일을 모두 `notified: true`로 바꾼다. 정리 문서 이름에는 해시를 모두 `-`로 잇는다.
- 정리집(`asset-index.json`)은 통째로 읽지 않는다. 조사할 자산(`new`가 아닌 것)마다 `"name": "<Name>"`을 검색해 그 항목 부분만 읽는다.
- 각 파일의 `changes` 중 `grade`가 `docs`인 항목은 대상에서 뺀다.
- 처리할 항목이 없으면 "조사할 변경이 없습니다"라고 알리고 끝낸다.
  (모든 항목이 `docs`인 기록 파일은 4단계 승인 없이 `notified: true`로 바꾸지 않는다. 다음 정리 때 함께 처리한다.)
- 조사할 항목(`new`가 아닌 것)이 있으면 `projects.json`을 읽는다. 없거나 프로젝트가 0개면 "projects.json에 스캔할 프로젝트를 등록해 주세요"라고 안내하고 끝낸다.
  신규 항목만 있으면 `projects.json`은 읽지 않는다.

### 2. 사용처 스캔 + 담당자 파악 (스크립트 한 번 실행)
1단계에서 정한 변경 기록 파일을 스크립트에 넘겨 한 번 실행한다. (common-repo에서 실행)

```
python tools/impact_scan.py --records <해시7>.json <해시7>.json
```

- 변경 기록 파일 이름만 적는다. (`asset-index/changes/` 안의 파일. 같은 자산은 스크립트가 알아서 하나로 묶고 등급은 가장 높은 것을 쓴다.)
- 자산 이름으로 바로 조회할 때(조회 모드)는 `--assets Pagination Holiday`로 쓴다. 변경 기록 없이 사용처만 찾는다.
- 결과는 stdout의 JSON이다. 진행 로그는 stderr에 나온다. 명령은 한 번만 실행하고, 결과를 파일로 저장하지 않아도 된다.
- 스크립트가 실패하면(오류 종료, JSON 아님) 실패 내용을 사용자에게 알리고 끝낸다. 직접 검색으로 대신하지 않는다.

스크립트가 하는 일은 복사본 찾기, import 찾기, 사용 줄 찾기, 정밀 확인, 기능 자산 스캔, 담당자 파악이다. (아래 [스크립트 결과 읽는 법] 참고)

### 3. 스크립트 결과 확인
JSON을 읽고 아래만 확인한다. 나머지는 그대로 쓴다.
- `assets[].error`가 있으면(정리집에 없는 자산) 그 자산은 "스캔 실패: <이유>"로 적는다.
- `assets[].projects[]`에 `ok: false`인 프로젝트는 "스캔 실패: <프로젝트> - <error>"로 적는다.
- `usages[]`마다 사용 방식(`kind`), 파일·줄(`lines`), 작성자(`authors`)를 그대로 문서 표에 옮긴다.
- `breaking`인데 `hit`이 `false`인 사용처 중 **사용 줄만 봐서는 바뀐 부분을 쓰는지 모르겠는 곳**은 해당 파일을 읽어 확인한다.
  그래도 애매하면 `hit: false`로 두고 문서에서 "확인 필요"로 적는다. (확인했다는 표시는 문서에 남기지 않는다.)
- 영향 대상(`usages`)이 0건인 자산은 문서에 "영향 대상 없음"으로 남긴다.
- 담당자는 `owners`에 있는 프로젝트(영향 대상이 있는 프로젝트)만 넣는다. 같은 사람(이메일 기준)은 한 번만 센다.

### 4. 미리보기 (사용자 확인 후)
저장할 정리 문서 **전문**(아래 [정리 문서 형식])을 **채팅 본문에 마크다운 그대로** 출력해 렌더링된 문서처럼 보이게 한 뒤,
질문 도구로 **"이대로 정리 문서를 만들까요?"** 한 줄만 묻는다.

- 미리보기 전체를 코드 블록(```)으로 감싸지 않는다. 감싸면 표·제목·굵게가 렌더링되지 않고 원문 글자가 보인다.
  코드 블록은 커밋 메시지처럼 그대로 복사해 쓰는 글에만 쓴다.
- 구조는 마크다운 요소(제목, 표, 인용, 굵게, 구분선 `---`)로만 만든다. 공백 정렬, 글자 구분선, `■`·`▸` 같은 기호 제목은 쓰지 않는다.
- 질문 창에는 긴 내용이 보이지 않는다. 질문 도구가 없으면 같은 질문을 채팅 본문 마지막 줄에 적고 답을 기다린다.
- **질문 전 확인**: 바로 위 응답 본문에 정리 문서 전문이 있는가? 없으면 질문하지 말고 문서부터 출력한다.

미리보기는 아래 세 부분으로 이어 붙인다. 1·3은 미리보기에만 있고 저장하는 문서에는 넣지 않는다.

1. **맨 위 안내** — 인용 블록 한 줄. 저장될 문서 이름을 알린다.
   ```
   > **영향도 조사·개발자 정리 미리보기** — 아래 내용이 `asset-index/notifications/20261014-635c4ba.md`로 저장됩니다.
   ```
2. **문서 전문** — [정리 문서 형식] 그대로. (`# 공통 변경 영향도 정리`부터 `## 스캔 결과`까지)
3. **맨 아래 저장 정보** — `---` 뒤에 아래를 붙인다. 커밋 메시지는 코드 블록으로 보여 준다.
   - **처리할 변경 기록**: 파일 이름 목록과 건수 (예: `635c4ba.json`, `b6a0f67.json` — 2건)
   - **정리 문서 커밋 메시지**

- 사용자가 수정을 요청하면 고친 뒤 미리보기를 다시 보여 주고 다시 묻는다.
- 사용자가 거절하면 아무 파일도 만들지 않고 변경 기록도 그대로 둔다.
- 영향 대상이 0곳인 항목도 문서에 "영향 대상 없음"으로 남긴다. 승인하면 처리한 것으로 본다.

### 5. 정리 문서 생성과 커밋
승인받은 내용 **그대로** 만든다.
- `asset-index/notifications/<YYYYMMDD>-<해시7들>.md`를 만든다. (UTF-8)
  - `<YYYYMMDD>`는 문서를 만든 날짜, `<해시7들>`은 포함된 변경 기록의 해시를 `-`로 이은 것.
- 처리한 변경 기록 파일마다 `notified: true`, `notifiedAt`(지금 시각, ISO 8601), `notification`(정리 문서 이름)을 넣는다.
  파일 편집 도구로 이 세 필드만 고친다. 다른 필드는 건드리지 않는다.
- 고친 변경 기록의 JSON이 올바른지 확인한다. (common-repo에서 실행)
  `node -e "for (const f of process.argv.slice(1)) JSON.parse(require('fs').readFileSync(f,'utf8')); console.log('JSON OK')" <변경 기록 파일들>`
- 정리 문서와 고친 변경 기록 파일**만** 커밋한다. 경로는 하나씩 적는다.
  ```
  git -C common-repo add <정리 문서> <변경 기록 파일들>
  git -C common-repo commit -m "<제목>" -m "<본문>" -- <정리 문서> <변경 기록 파일들>
  ```
  - 제목: `docs: 공통 변경 영향도 정리 (<해시7들>)`
  - 본문: 자산마다 한 줄.
    - 조사한 자산: `- <자산> [<등급>]: <N>곳, 프로젝트 <M>개, 관련 개발자 <K>명`
    - 신규 자산: `- <자산> [신규]`
  - 메시지는 `-F` 파일 대신 `-m`을 두 번 써서 명령 인자로 넘긴다. 커밋 직후 `git -C common-repo log -1 --format=%B`로 한글이 깨지지 않았는지 확인한다.

### 6. push 확인
- `git -C common-repo log --oneline @{u}..HEAD`로 push 안 된 커밋을 확인한다. upstream이 없으면 묻지 않고 보고에 적는다.
- 있으면 목록을 보여 주고 **"push할까요?"** 를 한 번만 묻는다.

### 7. 결과 보고
- 정리 문서 이름
- 자산별 등급과 영향 대상 수 (프로젝트, 파일). 신규 자산은 "신규"로만 적는다.
- 관련 개발자 목록
- 스캔 실패한 프로젝트와 이유
- push 결과

### 8. 이어서 알림 메시지 초안 (정리 모드에서 문서를 만든 경우만)
결과 보고 끝에 **"이어서 개발자별 알림 메시지 초안을 만들까요?"** 를 한 번만 묻는다. (신규 자산만 있는 문서도 묻는다. 전체 공지용 메시지 초안을 만들 수 있기 때문이다.)
- 승인하면 `common-asset-dispatch` 스킬을 호출한다. 대상은 **방금 만든 정리 문서만**이다. (문서 이름을 범위로 넘긴다.)
- 거절하면 끝낸다. 나중에 "알림 메시지 만들어줘"라고 따로 요청해도 `common-asset-dispatch`가 같은 문서를 처리한다.
- 메시지 초안 생성·저장·커밋은 `common-asset-dispatch`의 절차(자체 승인 포함)를 따른다. 이 스킬에서 직접 만들지 않는다.

## 스크립트 결과 읽는 법

```
{
  "assets": [{
    "name": "PageRequest", "type": "backend-module", "grade": "breaking",
    "commits": ["6731a2f"], "summaries": [...], "actions": [...],
    "scanHints": ["of"], "affectedApi": [],
    "usages": [{
      "project": "shop-app", "file": "backend/.../OrderController.java",
      "lines": [{"line": 11, "code": "PageRequest pr = PageRequest.of(page, size);"}],
      "kind": "import",            // import / copy / copy-modified / api-call
      "copiedFrom": null,          // copy일 때 공통 원본의 어느 커밋 버전인지
      "hit": true,                 // breaking에서 바뀐 부분을 쓰면 true

  "projects": [...]

```

- `kind`가 `copy` / `copy-modified`이면 공통 원본을 복사해 쓰는 파일이다. 조치는 `🟡 확인 필요`.
- `kind`가 `import` / `api-call`이고 `hit`이 `true`이면 `🔴 수정 필요`, 아니면 `🟡 확인 필요`. (`breaking`일 때)
- 기능 자산(`*-feature`)은 스크립트가 시작 클래스(Service·Util 등)의 import와 HTTP 호출(`api-call`)을 함께 찾는다.
- 스크립트가 보는 것은 **커밋된 코드뿐**이다. 프로젝트 저장소는 읽기만 한다.
- 스크립트는 파일 이름이 공통 원본과 다른 복사본(이름을 바꿔 복사한 코드)은 찾지 못한다. 문서에 이런 경우를 추측해서 넣지 않는다.

- **자산 섹션**: 조사한 자산은 `변경 내용`, `할 일`, 영향 대상 표를 쓴다. 신규 자산은 한 줄 설명만 쓰고 표를 만들지 않는다.
  - 묶인 기록이 여러 건이면 `변경 내용`에 커밋 시각 순으로 한 줄씩 적고, 제목에 해시를 모두 적는다.
  - `조치` 열은 `breaking`과 `behavior` 항목에 쓴다. `breaking`은 `hit`이면 `🔴 수정 필요`, 사용은 하지만 바뀐 부분을 쓰지 않거나 복사본이면 `🟡 확인 필요`로 정하고, `behavior`는 사용하는 곳 모두 `🟡 확인 필요`로 쓴다. 그 외 등급은 `-`로 둔다.
  - 파일 경로·줄 번호·코드는 `` `백틱` ``으로 감싼다.
  - 사용 방식이 `api-call`이면 사용 방식 칸에 `API 호출 (<METHOD> <경로>)`로 적는다.
  - 영향 대상이 없으면 표 대신 "영향 대상 없음"으로 쓴다.
- **수정 필요와 확인 필요를 나눠 표시한다:** `breaking` 항목에서 `조치`가 `🔴 수정 필요`인 곳만 수정이 필요한 곳이다.
  `확인 필요`(사용은 하지만 바뀐 부분은 쓰지 않음, 복사본)인 곳은 수정 필요로 세지 않는다.
  - `한눈에 보기`의 영향 대상 칸: `수정 필요 N곳 · 확인 필요 M곳 (프로젝트 K개)`. 한쪽이 0이면 그 부분은 쓰지 않는다.
  - `관련 개발자`의 자산 칸: 수정 필요인 곳은 등급 이모지(🔴), 확인 필요인 곳은 `확인 필요`로 쓴다.
    한 사람이 두 종류에 모두 해당하면 수정 필요를 우선한다. 담당자는 그 프로젝트에 수정 필요가 하나라도 있으면 🔴, 없으면 `확인 필요`.
  - `compatible` 항목은 이 구분을 하지 않고 등급 이모지를 그대로 쓴다. (`behavior`는 사용하는 곳을 모두 `🟡 확인 필요`로 쓴다.)
- **관련 개발자**: 개발자 × 프로젝트마다 한 줄. 같은 사람(이메일 기준)이 같은 프로젝트에서 여러 자산에 해당하면 한 줄에 모은다.
  담당자는 이름 뒤에 `(담당자)`를 붙이고 위치 칸에는 그 프로젝트의 해당 곳 수를 쓴다. 조사한 자산이 하나도 없으면 이 섹션은 만들지 않는다.
- **스캔 결과**: 프로젝트별로 `✓` 또는 `스캔 실패: <이유>`. 조사한 자산이 없으면 이 섹션은 만들지 않는다.
- 이메일, 커밋 메시지, 근거 메모는 문서에 넣지 않는다.

## 하지 말 것
- 프로젝트 저장소를 수정하거나, 프로젝트 저장소에서 커밋·checkout·pull 하지 않는다.
- 알림 문구(제목·본문)를 만들거나 메일, 메신저, PMS로 보내지 않는다. 알림은 이 스킬의 범위가 아니다.
- 신규 자산에 대해 사용처 스캔이나 대체 후보 탐색을 하지 않는다.
- 변경 기록의 `notified`·`notifiedAt`·`notification` 외 필드를 고치지 않는다. 정리집(`asset-index.json`)을 고치지 않는다.
- 스캔에서 나오지 않은 사용처나 담당자를 넣지 않는다.
